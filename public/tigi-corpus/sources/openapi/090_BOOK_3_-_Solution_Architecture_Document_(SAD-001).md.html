# Chapter 14. Integration Architecture Principles

所有整合均須遵循以下架構原則：

### IA-01 API First

所有跨平台互動應以正式 API 或受治理的事件介面進行。

禁止直接存取其他平台的內部資料或資料庫。

---

### IA-02 Canonical Data Exchange

跨平台交換資料時，應使用 TIGI Canonical Data Model。

平台不得自行定義不同語意的核心資料。

---

### IA-03 Loose Coupling

各平台彼此獨立部署、獨立演進。

任何平台失效，不得導致其他平台資料損毀。

---

### IA-04 Traceable Communication

所有跨平台呼叫均須具備：

- Correlation ID
- Trace ID
- Timestamp
- Request Source
- Request Target

以支援完整追溯。

---

### IA-05 Governance Enforcement

涉及案件狀態、Gate、Checklist、Evidence、PGP 的整合請求，均須經 Governance Core 驗證。

---

# Chapter 15. Platform Integration Model

正式整合架構如下：

```text
StyleMatch AI
        │
        ▼
Integration Service
        │
        ▼
Governance Core
        │
 ┌──────┼──────┐
 ▼      ▼      ▼
TWCID  iSAFE  AI Platform
        │
        ▼
Knowledge Graph
```

Integration Service 為跨平台入口，不直接承載業務邏輯。

---

# Chapter 16. Integration Categories

定義四類正式整合：

### IC-01 Internal Platform Integration

平台內部服務整合。

例如：

- StyleMatch AI ↔ Governance Core
- iSAFE ↔ Notification Service

---

### IC-02 Cross-Platform Integration

平台之間整合。

例如：

- StyleMatch AI → TWCID
- TWCID → iSAFE
- iSAFE → AI Platform

---

### IC-03 External System Integration

與第三方系統整合，例如：

- 電子簽章
- 金流服務
- 簡訊／電子郵件
- 雲端儲存
- 地圖服務

整合方式由 OpenAPI 與 Integration Specification 定義。

---

### IC-04 AI Integration

AI 模組整合，包括：

- LLM
- Vision AI
- OCR
- Knowledge Graph
- Agent Framework

AI 元件不得直接修改治理狀態。

---

# Chapter 17. Integration Boundaries

各平台責任邊界如下：

**StyleMatch AI**

- AI 分析
- 需求蒐集
- 風格建議

不得直接修改專案治理狀態。

---

**TWCID**

- 會員
- 認證
- 媒合

不得直接控制工程流程。

---

**iSAFE 2.0**

- 專案治理
- 狀態控制
- Gate
- Checklist
- 驗收
- 保固

不得自行修改 AI 推論結果。

---

**AI Platform**

- AI 推論
- 知識服務
- 智慧建議

不得直接執行業務交易。

---

# Chapter 18. Integration Contracts

所有整合介面均須建立正式契約（Integration Contract），至少包含：

- Contract ID
- Source System
- Target System
- Interface Type
- Canonical Data Model
- Authentication
- Authorization
- Error Handling
- Version
- Traceability

詳細欄位由 OpenAPI Specification 定義。

---

# Chapter 19. Event Integration

所有跨平台事件應以正式事件模型管理，例如：

- EVT-001：CaseCreated
- EVT-002：RequirementConfirmed
- EVT-003：DesignerMatched
- EVT-004：ContractSigned
- EVT-005：GatePassed
- EVT-006：ChecklistCompleted
- EVT-007：PaymentApproved
- EVT-008：InspectionCompleted
- EVT-009：WarrantyStarted
- EVT-010：CaseClosed

事件詳細結構由 DDS 與 OpenAPI 定義。
